### Stories the numbers tell

- **Q2 ST_Subdivide.** GiST on parcels cuts the full scan (2,722 -> 465 ms at SF1, 16,414 -> 3,924 ms at SF5), but what remains is the exact ST_DWithin test against two large, complex project polygons (the airport site and the textile park, the only active projects): explain_q2_sf5 shows 110,150 candidate pairs from 2 projects. Splitting the project geometry into 18 small pieces (ST_Subdivide on ST_Segmentize, own GiST) gives more pairs (464,630) but each test is cheap: 364 / 2,161 ms (1.3x / 1.8x faster than plain GiST). The precomputed `parcel_project_impact` lookup skips geometry entirely: 20 / 91 ms (it measures from parcel centroids, so its count differs slightly from the geometry variants). Before the M5 data change (5 active projects including two ring roads) plain GiST helped far less, because a ring road's bounding box covers most of the core (earlier SF1 run, recorded in the build notes).
- **Q6 selective vs broad.** With the covering index I5, a selective filter returns page 1 in 3.517 / 2.12 ms (SF1 / SF5) against 93.347 / 105.285 ms without it. For the broad filter the gain is smaller (11.274 vs 87.916 ms at SF1, 70.605 vs 132.882 ms at SF5): the index orders by (land_type, zone_code, cagr_5y) but the filter ranges over several zones and a distance, so many index entries are read and then filtered (explain_q6_sf5: 'Rows Removed by Filter: 32646' per worker).
- **Keyset vs OFFSET.** Page 50 with keyset: 17.41 / 60.989 ms; with OFFSET 2450: 21.69 / 114.117 ms. OFFSET must produce and discard 2,450 rows (top-N heapsort memory grows from ~31 kB to ~550-715 kB in explain_q6_sf5); keyset starts at the cursor.
- **BRIN vs B-tree (Q7).** BRIN 4.314 / 18.525 ms, B-tree 2.626 / 7.759 ms, no index 3.284 / 17.653 ms. Yearly partitions already prune to one year, so BRIN's block ranges save little and its lossy bitmap rechecks rows: BRIN is slower than both the B-tree and a plain scan of the partition at SF1 and SF5. Its advantage is size: 0.45 MB against 2.66 / 12.44 MB for the B-tree twin.
- **Q8 retrieval (149 chunks).** Keyword 0.516 ms, exact vector scan 1.897 ms, HNSW 0.744 ms, spec hybrid 2.768 ms, the API's statement 2.536 ms (SF1). HNSW recall@10 = 1.0 vs the exact scan (avg of 20 query vectors). On 149 chunks the planner scans the table for the keyword query too (GIN unused). Retrieval quality per method is in section 7.
- **Index bloat from REFRESH CONCURRENTLY.** The benchmark measured `pm_screener_ix` at 33.95 / 89.48 MB (sf*.csv, index_size_mb) after many concurrent refreshes during the build; migration 015 later recreated the view and the fresh index is 6.45 / 32.08 MB (section 3). CONCURRENTLY rewrites changed rows instead of swapping the heap, so its indexes bloat; a periodic REINDEX CONCURRENTLY or a plain REFRESH in a maintenance window reclaims it.

### Results that need explaining (planner's reason from EXPLAIN)

1. **Q3 KNN comparables is 794 ms at SF5 (145 at SF1, of which JIT ~81 ms in explain_q3_sf1), but the query work is ~2 ms: the time is JIT compilation.** The plan touches 20 parcels and 364 buffers, yet the planner's total cost estimate (619,100, from the LIMIT over a KNN scan with a per-row LATERAL) exceeds `jit_above_cost` (100,000), so Postgres JIT-compiles 48 functions. Same prepared query on SF5 with `jit = on`: 1,086 ms (JIT total 1,051 ms); with `SET jit = off`: 1.9 ms (manual EXPLAIN ANALYZE, 2026-11-24). Fix: `jit = off` (or a much higher `jit_above_cost`) for this OLTP workload; not applied, so the committed numbers stay comparable. The report endpoint's comparables query has the same shape.
```
Limit  (cost=8.45..619100.36 rows=10 width=60) (actual time=648.985..649.589 rows=10 loops=1)
        ->  Limit  (cost=8.04..10.28 rows=1 width=72) (actual time=0.030..0.030 rows=0 loops=20)
JIT:
  Timing: Generation 4.394 ms (Deform 1.346 ms), Inlining 103.585 ms, Optimization 421.138 ms, Emission 356.314 ms, Total 885.431 ms
Execution Time: 887.080 ms
```
2. **Q3 ORDER BY ST_Distance** (2,916 ms at SF5): without the `<->` operator the planner cannot use KNN; it fetches every parcel within 5 km (165k at SF5), runs the LATERAL sale lookup for each, then sorts. JIT adds ~1.9 s at SF5 here too.
```
              ->  Gather  (cost=3759.40..990657.15 rows=38 width=40) (actual time=47.142..123.327 rows=164947 loops=1)
  Timing: Generation 7.223 ms (Deform 2.546 ms), Inlining 605.897 ms, Optimization 717.040 ms, Emission 564.514 ms, Total 1894.674 ms
Execution Time: 4308.313 ms
```
3. **BRIN slower than the B-tree and than a plain scan (Q7).** Partition pruning leaves one year (the 2024 partition, 1,178 pages at SF5); BRIN marks 410 of them as candidates (lossy) and rechecks 10,277 rows away, while the B-tree reads ~317 buffers exactly.
```
        Rows Removed by Index Recheck: 10277
        Heap Blocks: lossy=410
Execution Time: 16.498 ms
```
4. **Q9 trigram index unused.** `village` has 185 rows (one or two pages); a sequential scan is cheaper than any index lookup, so the GIN index only matters at larger village counts.
```
        ->  Seq Scan on village  (cost=0.00..8.31 rows=1 width=30) (actual time=0.531..0.532 rows=0 loops=1)
Execution Time: 0.561 ms
```
5. **Q8 HNSW vs exact.** With 149 chunks the exact scan is ~1.897 ms; the benchmark forces the index (`enable_seqscan = off`) to measure HNSW, and recall@10 is 1.0. The index pays off only at thousands of chunks.

6. **pgbench levels off.** From 8 to 32 clients throughput rises only 16% at SF1 (279 -> 324 TPS) while average latency grows 3.4x (29 -> 99 ms), so the server is already near capacity at 8 clients; extra clients queue. pgbench ran inside the db container on the same 12-core laptop as the stack. Each transaction is a broad screener page (peri-urban, within 3 km, a random growth floor), which reads thousands of index entries: the benchmark's Q6 page 1 at SF1 keeps 11,447 and filters 5,325 (explain_q6_sf1); pgbench's own filter differs, so this shows the order of magnitude only (source: pgbench CSVs above).

## 5. Transactions

**Purchase transaction** (spec 2.11; implemented in `api/landlens/app/routers/credits.py`), READ COMMITTED:

```sql
BEGIN;
SELECT credit_balance FROM app_user WHERE user_id = $u FOR UPDATE;   -- serializes this user's purchases
-- already unlocked -> COMMIT, charged 0;  credit_balance < 1 -> ROLLBACK, 402
INSERT INTO report_unlock (user_id, parcel_id, credits_spent) VALUES ($u, $p, 1);
INSERT INTO credit_ledger (user_id, delta, reason, parcel_id, idempotency_key) VALUES ($u, -1, 'report_unlock', $p, $key);
```

**Retrieval design** (source: `api/landlens/app/services/rag.py`, spec 2.13, ADR-012): PyMuPDF text blocks, ~400-token chunks with 15% overlap, cut early at headings; `text-embedding-3-small` (1536 dims). One SQL statement fuses the top 40 keyword candidates (`ts_rank_cd` over a GIN `tsvector`) and the top 40 vector candidates (HNSW cosine) by Reciprocal Rank Fusion (k = 60), returns the top 6 plus the keyword hit count and the best cosine distance. Generation (`LLM_MODEL`, default gpt-4o-mini, temperature 0) sees only numbered excerpts; every `[n]` is checked against the excerpts given; unknown numbers are dropped, none left -> excerpts without an answer. No key or an outage -> degraded keyword-only mode (same statement, OR-ed terms).

**Not-found rule:** no keyword hit AND best cosine distance > 0.6 (`CHAT_MAX_DISTANCE`) -> "not found in the documents" without calling the LLM.

**Eval** (source: `bench/results/rag_eval.json`, the latest `make eval` run, 2026-11-23, gpt-4o-mini, threshold 0.6; questions in `bench/rag_eval_questions.json`, 20 answerable + 5 not):

## 10. Known limitations and V1

Source: the build notes' known issues, `SECURITY.md` residual risks, the V1 roadmap.

- All land data is synthetic (no OSM export, projects GeoJSON or zone list supplied); price bases are placeholders, not calibrated to published Warangal rates.
- JIT compilation dominates the comparables (KNN) query at SF5 (~0.9 s of ~0.9 s); `jit = off` would fix it (not applied).
- BRIN on sale dates is slower than a B-tree on yearly partitions; kept for size and as a measured comparison.
- Corpus: no G.O.Ms.No.202 / KUDA zoning regulations, so zone-specific rules (setbacks, permitted uses) are usually 'not found'; AP Act 2006 pages 7-12 have no text layer (no OCR); the Bhu Bharati Act is a noisy OCR scan.
- RAG: keyword recall@10 only 30% (websearch AND semantics), so hybrid adds nothing over vector on this eval; 4/20 answers wrong or partly wrong in the last eval; the prompt fix is unmeasured.
- Security residuals: no HTTPS locally; CSP keeps script-src 'unsafe-inline'; rate limits in memory per worker; JWTs not revocable before expiry; Swagger public unless API_DOCS=false.
- Agricultural parcels (146 at SF1) sit mostly in one village; their cagr_5y distribution is narrow.
- No point-in-time recovery demo; watchlist (stretch) not built; responsive layout below 900 px not walked; J3 not walked live with a key by the agent.

**V1** (spec 3.6): scraping pipeline (guideline rates, KUDA/MA&UD orders, project news) after a terms-of-use review, through the existing staging/upsert path; real OSM, project geometry and zone legend inputs; watchlist alerts (event table matched against watchlists, email); ML valuation (gradient-boosted quantiles, SHAP drivers) only if it beats the rule-based baseline on real data; parcel chat over parameterized queries; PDF highlighting; Razorpay test mode and PDF export; hosted VPS with HTTPS and HSTS, Playwright smoke tests, mobile layout; nonce-based CSP; token revocation.
